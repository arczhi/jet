01 / The loop

What happens in one request?

Instead of endlessly growing a transcript, jet rebuilds a right-sized working window from durable state at every step.

01

Persist state

User requests, tool results, and plan nodes become SQLite chunks.

02

Choose context

The judge decides which history should be hidden, noted, summarized, or kept in full.

03

Choose tools

Every tool has a compact description; only likely tools receive full schemas.

04

Do the work

The worker streams output; policy checks happen before writes or commands execute.

05

Verify results

The goal, answer, and evidence are checked with bounded retries.

02 / RLCD

History is not flattened,
only re-presented for a moment.

A normal summary can overwrite old information. jet keeps the original and treats a summary as a temporary view for one request.

Chunk tree

Every fact has an identity, type, order, and parent. Context is selected from this tree.

USERFix the login test
TOOLpytest failure output
SUBGOALLocate token expiry logic

Four attention levels

The judge supplies scores; code owns thresholds. Content is compressed only when the budget really overflows.

HideNot relevant to the current goal; leave it out for now.
One-line noteKeep only its existence and conclusion.
SummaryRelevant, but the full detail is unnecessary.
Full textKey evidence, the current task, and pinned content.
03 / Division of labor

Three roles, three strengths.

Separate judgment from creation so the expensive model does not handle every tiny decision.

CHEAP + FREQUENT

Judge

Structured decisions: relevance, tool routing, plan gating, permission advice, and completion checks.

EXPENSIVE + FOCUSED

Worker

Reads a focused context, writes code, calls tools, and answers the user. Cost is spent on real work.

DETERMINISTIC

Code

Owns thresholds, budgets, recursion depth, permission rules, duplicate-call refusal, and stop conditions.

04 / Safety boundary

The model can advise,
but it cannot quietly approve.

For writes and commands, decisions only move toward stricter safety. Deterministic rules always come first.

① Deterministic rulesBlock clear risks such as sudo, dangerous recursive deletion, and piping remote content into a shell.
② Judge safety adviceCatch potential leaks, damage, or privilege escalation that rules did not anticipate; only tighten the result.
③ Human approvalAsk mode sends the call to a person; with no approver, the call is denied and the system fails closed.
05 / Why it matters

The innovation is not a buzzword,
but the combination of boundaries.

Each mechanism is familiar on its own. The difference is an observable, bounded, recoverable loop that combines them.

06 / Open the hood

When you want depth, open these files.

This visual guide explains the ideas; the Markdown and source code keep the exact details.

How is context selected?
src/jet/context/attention.py scores and renders four levels; src/jet/context/builder.py handles token budgets, protocol-safe message blocks, and the final prompt.
Why does planning not slow simple tasks?
src/jet/context/decompose.py asks the judge whether planning is needed and runs it alongside the first generation step. Depth, total nodes, deduplication, and actionability are bounded.
How is a tool call recorded?
src/jet/agent/loop.py executes, persists, and refuses duplicate calls; src/jet/policy/permissions.py handles rules, judge advice, and human approval.
How do we know the agent actually finished?
src/jet/agent/verify.py supports both judge and independent LLM verification; malformed or unavailable provider results are explicitly marked inconclusive.
The short version

Keep the full case file on the shelf; hand the model only the pages it needs.

That is jet's core: durable state + lightweight judgment + focused execution + evidence-based verification. Probabilistic advice, surrounded by deterministic code boundaries.
